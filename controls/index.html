Access boundary

Read records. Propose changes. Keep execution outside.

The first proposed pilot reads permissioned bank statement and GL exports for one entity. Payment initiation, bank rails and ERP writes are excluded. A future integration would require a separately agreed scope and access review.

  • Read-only historical inputs
  • Draft classifications and journal proposals
  • No fund movement, posting or payment-file transmission
Source integrity

An old source never earns a fresh label.

Show source cutoff, expected update and review time separately. Retain the stale warning in the exception view and exported memo. A reviewer can record what the available evidence supports without certifying a current cash position.

Human authority

Two identities must mean two reviewers.

The proposed payment-file review keeps first and second reviewers distinct. Changes to the reviewed file invalidate dependent approvals. Review acknowledgment does not grant release authority or demonstrate that CashVariance controls an external bank process.

Review history

Keep the reason beside the revision.

A reviewer override records the original suggestion, revised disposition, reason and timestamp. Source values remain unchanged. A draft journal stays unposted; a missing confirmation stays visible until separate evidence supports it.

Before real data

Agree the handling before receiving a file.

Security architecture, operator details, retention and transfer arrangements must be finalized for any real pilot. No certification, production integration or completed security review is claimed by this concept.

  • Confirm bank and ERP file-sharing rights
  • Name the treasurer and payment-control owner
  • Agree least-privilege access, deletion and retention
  • Obtain treasury and security approval
